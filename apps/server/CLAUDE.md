# Deck-Legacy Server — AI Assistant Guide

NestJS 11 API (`@deck-legacy/server`). Games are played on devices (offline included); the server receives each game's event log, **replays it with the engine to validate it**, stores it in PostgreSQL through Prisma 7, computes scores for the leaderboard and verifies Supabase access tokens. It runs the player commands recorded in the log again to verify it (EDR-051), never commands sent apart from a log.

Repository-wide rules (engine, `GameSession`, layers, TypeScript, lint, quality gates) are in the [root `CLAUDE.md`](../../CLAUDE.md).

---

## Quick Reference

From the repository root:

```bash
pnpm db:up                                  # Local PostgreSQL (docker-compose.yml)
pnpm db:migrate                             # prisma migrate dev
pnpm dev:server                             # Build packages, generate Prisma client, nest start --watch (port 3000)
pnpm build:server                           # Packages + server → apps/server/dist
pnpm --filter @deck-legacy/server test      # Unit + e2e tests (no database or Supabase needed)
pnpm --filter @deck-legacy/server prisma:deploy   # Apply migrations (production)
pnpm generate:api                           # Rewrite openapi.json (via the e2e test) and the client API types
```

NestJS stays on **v11 (CommonJS)**: v12 is ESM-only, which the extensionless imports of the engine package do not support.

```text
│   │   ├── infrastructure/# PrismaGamesRepository (implements the GamesRepository port)
│   │   ├── presentation/  # GamesController (HTTP + Swagger decorators), dto/ (zod schemas that `satisfies` the models)
│   │   └── games.module.ts
│   ├── users/  scores/    # Same layout: application/ (service + models/), presentation/ (controller + dto/)
│   ├── prisma/            # PrismaService (pg adapter), Transaction type, JSON mappers shared by modules
│   ├── shared/            # presentation/http/ (ZodValidationPipe, ApiExceptionFilter, ApiErrorDto, nullableStringSchema), trim-trailing-slashes
│   └── generated/prisma   # GENERATED Prisma client (gitignored, `prisma generate`)
├── prisma/                # schema.prisma + migrations
├── openapi.json           # HTTP contract (GENERATED, committed; checked by tests/games.e2e.test.ts)
└── tests/                 # Unit + e2e tests
```

Imports inside the server are relative; shared code comes from `@deck-legacy/engine/*` and `@deck-legacy/game-data`. Request and response DTOs live in `<module>/presentation/dto/`, one per file (EDR-056, 058). Use cases take and return the plain types of `<module>/application/models/`; each DTO schema `satisfies z.ZodType<Model>`, so the compiler keeps the HTTP contract and the models in line without mapping code.

**Structure rules (EDR-057).** One public export per file (a class, a function or a constant, plus its own types); file names are kebab-case with the Nest role suffix (`sync-game.use-case.ts`, `prisma-games.repository.ts`, `games.controller.ts`, `game-summary.dto.ts`, `game-lock.ts`); no `common/`/`helpers/`/`utils/` folders. Layers inside a feature module: `presentation → application → domain`, `infrastructure → application`; a use case depends on a port (abstract class used as the injection token), never on Prisma code of its module. dependency-cruiser enforces the layers, ESLint forbids Nest, zod and Prisma in `domain/` and more than one class per file.

## Game Sync

- `PUT /games/:id` receives the events of a game from `fromSeq` on (the stored events before `fromSeq` are kept), card names and kingdom name. With `baseVersion`, a sync built on another `Game.version` is refused with `409 STALE_VERSION`, as is a `fromSeq` past the stored log; without it (clients older than the delta sync, or the player chose to overwrite) the sync overwrites the game. The id is generated by the client; the first sync creates the game. A player keeps several games (**kingdoms**, EDR-038): at most 10 non-abandoned games for a registered account and 1 for a guest. Creating (or re-activating an abandoned) game above the limit is refused with `409 KINGDOM_LIMIT`.
- `SyncGameUseCase` (with `GameValidator.validate`) rebuilds the full log (stored prefix + received events) and checks it with `GameSession.verify()` and the bundled catalog (`loadGameCatalog()`): the recorded commands are run again from the seed of `GAME_STARTED` and must produce the received events, or the log is refused (`422 INVALID_GAME`). A log without a seed (started before EDR-051) is only replayed with `GameSession.restore()` and stored with `Game.verified = false`, out of the leaderboards. A log using development cheats (events tagged `cheat`, or older `cheat_*` card actions) is refused unless `ALLOW_CHEATS=true` (then only replayed).
- **Checkpoint** (EDR-052): `Game.checkpointSeq` / `checkpointState` hold the state after the commands that drew the first turn of the last round (`checkpointSeq()` of the engine). While the incoming log keeps the events it covers (`firstDifference` ≥ `checkpointSeq`), `validate` passes it to `verify()` / `restore()`, which only run what follows; otherwise the whole log is checked. After each accepted sync, the checkpoint moves to the last round, rebuilt from the previous one, so a checkpoint corrected by the maintainer in the database carries over. `GET /games/:id/export` sends it: the client resumes the game from it (EDR-053). A manual correction must also bump `Game.version`, so devices download it.
- The score, the finished flag and `gameState.campaignScores` come from the server's own run (re-execution, or replay for unverified games), never from the client. Campaign scores are mirrored into `Score` in the same transaction. `Game.segments` stores the segment scores in the order they were played (`GameSession.getCampaignSegments()`), for the client's home page.
- The repository rewrites the stored log from the first event that differs (`firstDifference`), so rewinds and appends only touch the changed tail. Each accepted sync bumps `Game.version`.
- **Optimistic versioning** (EDR-041): a device that is behind gets `409 STALE_VERSION` and the player chooses which version to keep (see `apps/client/CLAUDE.md`). Syncs of the same game are serialised by an in-memory lock (`GameLock`), which assumes a **single server instance**.
- Re-execution proves every move was legal for the engine, not that the player did not know the seed (it is in the log). It is only as strong as the engine's input checks (`packages/engine/src/application/session/input/`). `tests/verification.fuzz.test.ts` plays random games on the real data and must keep verifying them.
- Engine or game-data changes must keep old event logs replayable, or synced games will be refused.

## HTTP API

| Route                              | Auth   | Purpose                                                  |
| ---------------------------------- | ------ | -------------------------------------------------------- |
| `GET /health`                      | public | Liveness                                                 |
| `GET /games`                       | user   | The player's kingdoms (non-abandoned games)              |
| `GET /games/current`               | user   | Latest non-abandoned game (older clients; `404` if none) |
| `PUT /games/:id`                   | user   | Sync a game's event log → `GameSummary`                  |
| `GET /games/:id/export`            | user   | Event log and card names (to resume on another device)   |
| `DELETE /games/:id`                | user   | Abandon a game (delete a kingdom)                        |
| `DELETE /games/current`            | user   | Abandon the latest game (older clients)                  |
| `GET/PATCH /me`                    | user   | Profile (display name)                                   |
| `DELETE /me`                       | user   | Delete the account (Supabase user + all its data)        |
| `GET /scores/me`                   | user   | Own final scores                                         |
| `GET /scores/leaderboard?segment=` | public | Best scores of registered (non-anonymous) players        |
| `GET /scores/kingdoms?limit=`      | public | Kingdoms of registered players with the best total score |

- Every route requires a token unless decorated with `@Public()` (global `AuthGuard`).
- Each body and response is a zod DTO (`createZodDto` from `nestjs-zod`) in `<module>/presentation/dto/`. Validate bodies with `new ZodValidationPipe(Dto.schema)`; document responses with `@ApiOkResponse({ type: Dto })`. Use `nullableStringSchema` for `string | null` (swagger reads zod's `['string', 'null']` as an array).
- After any route or DTO change, run `pnpm generate:api`: it rewrites `openapi.json` and the client types (`apps/client/src/infrastructure/api/generated`). CI fails when either is stale.
- Swagger UI: `/docs` (JSON: `/docs-json`), public.
- Errors always use the `ApiErrorBody` shape (`ApiExceptionFilter`).
- CORS: `CORS_ORIGINS`, plus any `localhost` port outside production (`is-allowed-origin.ts`). The JSON body limit is 20 MB (long games produce large logs).

## Authentication

- `SupabaseTokenVerifier` checks the access token: issuer `${SUPABASE_URL}/auth/v1`, audience and role `authenticated`. It uses the project JWKS (`SUPABASE_JWKS` provider; Supabase signs with ES256), never a shared secret.
- `AuthGuard` then calls `UsersService.ensureUser`, which upserts the `User` row (id = Supabase `sub`, email, `isAnonymous`) and caches it in memory to avoid one write per request.
- Anonymous (guest) users can sync games and have scores, but are excluded from the leaderboard.
- `DELETE /me` deletes the Supabase user through the admin API, then the `User` row; games, events and scores follow by cascade.

## Database (Prisma)

Schema: `prisma/schema.prisma`; config: `prisma.config.ts`; client generated to `src/generated/prisma` (CommonJS, `prisma-client` generator) and instantiated with the `@prisma/adapter-pg` driver adapter in `PrismaService`.

| Model       | Contents                                                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `User`      | Supabase user id, email, display name, anonymous flag                                                                                    |
| `Game`      | Owner, status (`ACTIVE`/`FINISHED`/`ABANDONED`), version, name, card names, score, ordered segments, verified flag, checkpoint (EDR-052) |
| `GameEvent` | Event log of a game (`gameId` + `seq`), JSON payload                                                                                     |
| `Score`     | Final score per game and campaign segment (`base` or an expansion)                                                                       |

Change the schema, then `pnpm db:migrate` to create a migration (commit it). Never edit an applied migration. PostgreSQL `jsonb` reorders object keys: compare events by content, not by serialised string.

## Configuration

`.env` (see `.env.example`), validated at startup by `src/config/env.ts`:

| Variable                    | Purpose                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| `DATABASE_URL`              | PostgreSQL connection string                                                                   |
| `SUPABASE_URL`              | Supabase project URL (token issuer and JWKS)                                                   |
| `SUPABASE_SERVICE_ROLE_KEY` | Optional secret key, only for `DELETE /me` (Supabase admin API); without it `DELETE /me` → 503 |
| `CORS_ORIGINS`              | Comma-separated allowed browser origins                                                        |
| `PORT`, `NODE_ENV`          | HTTP port, environment                                                                         |
| `ALLOW_CHEATS`              | Accept logs played with the cheat panel; forced off in production                              |

## Deployment

Google Cloud Run + Supabase (EDR-035). When a `v*` tag is pushed, the `deploy-api` job of `.github/workflows/deploy.yml` (after CI, behind the `production` environment's required reviewer) runs `prisma:deploy` against Supabase, builds the root `Dockerfile`, pushes it to Artifact Registry (`deck-legacy` repository) and deploys the `deck-legacy-api` service with `--max-instances=1` (in-memory locks).

- GitHub variables: `GCP_PROJECT_ID`, `GCP_REGION`, `GCP_WIF_PROVIDER`, `GCP_DEPLOY_SERVICE_ACCOUNT`, `SUPABASE_URL`, `API_URL` (Cloud Run URL, used by the web build). GitHub secret: `DATABASE_URL` (migrations only).
- Runtime secrets live in Google Secret Manager: `deck-legacy-database-url`, `deck-legacy-supabase-service-role-key`.
- `DATABASE_URL` is the Supabase **session pooler** URL (port 5432): Cloud Run has no IPv6 for the direct connection, and the transaction pooler (6543) does not support migrations.
- Local check: `docker build -t deck-legacy-api .` then `docker run -p 3000:8080 -e PORT=8080 -e DATABASE_URL=… -e SUPABASE_URL=… deck-legacy-api`.

## Common Pitfalls

- **The runtime uses the packages' `dist/`.** After changing `packages/*`, rebuild (`pnpm build:packages`) or restart `pnpm dev:server`.
- **Deploy the server with the same engine and game data as the clients**, or valid games may be refused.
- **Run `prisma generate` after a schema change** (the `typecheck`, `test`, `build` and `dev` scripts do it).
- **NestJS provider keys (`useFactory`, `useValue`) are not React hooks**: the related lint rule is disabled for server code.
